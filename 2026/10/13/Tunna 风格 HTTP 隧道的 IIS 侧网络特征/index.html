Tunna 风格 HTTP 隧道的 IIS 侧网络特征

样本信息

  • 原始文件：tunna_iis_rdp_smb_tunneling_sysmon_3.evtx

  • SHA-256：d7e75b35f9db32c91dc0d066ee935b382253fb56659f19c05833c964f8217469

  • 文件大小：69,632 字节（68 KiB）

  • 文件格式：Windows EVTX；文件头显示 1 个在用 Chunk

  • 有效 EVTX 记录：12 条；物理记录头 Record ID 1—12，连续，记录起点为 0x1200，最后一条记录结束于 0x3AA0

  • 事件提供程序：Microsoft-Windows-Sysmon

  • 日志通道：Microsoft-Windows-Sysmon/Operational

  • 日志主机：MSEDGEWIN10

  • 记录类型：均为 Sysmon Event ID 3 / Network Connection（网络连接）

  • 主要 UTC 时间：2019-09-03 11:04:05.797—11:36:24.649（依据 EventData.UtcTime）

  • 对应北京时间：2019-09-03 19:04:05.797—19:36:24.649（UTC+8）

  • 主机网络地址线索：10.0.2.15；本地回环 127.0.0.1；广播地址 10.255.255.255

  • 关键 IIS 身份：IIS APPPOOL\DefaultAppPool

Tunna 原理：SECFORCE 的 Tunna 是一种将 TCP 应用数据封装在 HTTP 请求和响应中的工具。其典型场景是：外部客户端访问 Web 服务器上的服务端脚本，由服务端脚本再连接 Windows 主机本地或其他可达 TCP 服务，将数据在 HTTP 与原 TCP 流之间转发

传统 IIS 网站处理请求通常不需要反复主动连接本机 RDP 和 SMB 端口

攻击链

IIS 工作进程第一次访问 RDP（Record 1—2）

Record ID 1，Sysmon Event ID 3：

  1. w3wp.exe 是 IIS 的工作进程；执行身份为 IIS APPPOOL\DefaultAppPool，表明连接由该应用程序池进程发起

  2. 3389/TCP 是常用 Windows RDP 服务端口，且事件明确给出服务名 ms-wbt-server

  3. 源和目的地址都是 127.0.0.1，连接发生在同一主机回环网络，不是 w3wp.exe 直接访问公网 IP

  4. Record 2 的源/目的 IP 与端口恰好镜像 Record 1，且 Initiated=false，支持它是同一次 TCP 连接的服务端侧记录

  5. svchost.exe 的 PID 8 是日志字段的原样值。由于缺少该 PID 的 Sysmon 1 / 服务配置证据，不应凭此进一步断言具体承载 RDP 的 Windows 服务实例或文件真伪

Record ID 2，接收端视角

IIS 工作进程第二次访问 RDP（Record 3—4）

Record ID 3：

Record 1 与 3 的 ProcessGuid、PID、Image、User 相同，说明它们由同一个已记录的 IIS 进程实例发起；仅源临时端口由 49947 变成 49948。两次 UtcTime 相隔 49.350 秒

IIS 工作进程访问本机 SMB（Record 7—10）

首次 SMB 连接：Record 7—8

第二次 SMB 连接：Record 9—10

SMB 阶段判断

  • 445/TCP 与 microsoft-ds 对应，通常关联 SMB 文件共享协议

  • PID 8892 的 IIS 进程两次发起本机 TCP 445 连接，源端口 49949、49950；两次连接间隔 73.064 秒

  • Record 7、9 具有相同的 ProcessGuid；但与 RDP 阶段的 PID 3008 / ProcessGuid 不同。从日志直接可知它们是两个不同的 IIS 进程实例，不能仅凭本文件说明为什么 PID 改变（例如应用程序池回收、重启或新工作进程）

  • 目的地址始终是 127.0.0.1，因此这里的 SMB 目标首先是日志主机本身，不是另一台内网机器

NetBIOS 名称服务流量（Record 5—6、11—12）

  • 端口 137/UDP：日志服务名为 netbios-ns，通常与 NetBIOS 名称解析有关

  • 主机侧 IP 10.0.2.15，目的地址 10.255.255.255 为广播形态的地址

  • 该行为可作为 Windows 网络背景，但它由 System 发起，没有与前述 w3wp.exe 相同的 ProcessGuid/PID

测验

题目 参考答案
1. 日志文件格式是什么？ Windows EVTX
2. 有多少条有效事件？ 12
3. 事件来源通道？ Microsoft-Windows-Sysmon/Operational
4. 本样本的 Event ID？ 3（Network Connection）
5. 日志所属主机？ MSEDGEWIN10
6. 主要可疑进程名称？ w3wp.exe
7. 可疑进程完整路径？ C:\Windows\System32\inetsrv\w3wp.exe
8. IIS 执行身份？ IIS APPPOOL\DefaultAppPool
9. RDP 目标地址？ 127.0.0.1
10. RDP 目标端口？ 3389/TCP
11. RDP 对应 Windows 服务名？ ms-wbt-server（日志端口名）
12. RDP 阶段 IIS 进程 PID？ 3008
13. RDP 阶段 ProcessGuid？ 747f3d96-48a4-5d6e-0000-001072958000
14. 第一次 RDP 发起端口？ 49947
15. 第二次 RDP 发起端口？ 49948
16. 与 RDP 连接匹配的服务端事件？ 物理 Record ID 2、4
17. RDP 服务端进程？ C:\Windows\System32\svchost.exe，日志 PID 8
18. SMB 目标地址与端口？ 127.0.0.1:445/TCP
19. SMB 端口服务名？ microsoft-ds
20. SMB 阶段 IIS 进程 PID？ 8892
21. SMB 阶段 ProcessGuid？ 747f3d96-4f81-5d6e-0000-001001818b00
22. 两次 SMB 连接源端口？ 49949、49950
23. SMB 接收端进程？ System（PID 4，NT AUTHORITY\SYSTEM）
24. 两个阶段是否同一个 PID？ 否：RDP 为 3008，SMB 为 8892
25. 两个阶段是否同一个应用程序池身份？ 是：IIS APPPOOL\DefaultAppPool
26. UDP 137 对应什么？ netbios-ns，NetBIOS 名称服务
27. 日志中出现的主机 LAN 地址？ 10.0.2.15
28. UDP 广播目的地址？ 10.255.255.255
29. 能否从日志找出外部攻击者 IP？ 不能；主要异常连接均走本机回环
30. 能否确定 WebShell 文件是 conn.aspx？ 不能；这是 Tunna 官方示例，不是本日志观察结果
31. 能否证明 RDP 登录成功？ 不能；须结合 4624/1149 等
32. 能否证明 SMB 认证成功或访问了共享？ 不能；须结合 5140/5145、文件/SMB 会话数据
33. 为什么怀疑 HTTP 隧道？ IIS w3wp.exe 主动连接本机 RDP 与 SMB，符合 Web 隧道服务端特征
34. 物理 Record ID 和 XML EventRecordID 是否相同？ 不同；物理 1—12，XML 为 35076 等
35. 最后一条记录头时间是否正常？ 否；物理 Record 12 的头部 FILETIME 为 0
36. SHA-256？ d7e75b35f9db32c91dc0d066ee935b382253fb56659f19c05833c964f8217469
