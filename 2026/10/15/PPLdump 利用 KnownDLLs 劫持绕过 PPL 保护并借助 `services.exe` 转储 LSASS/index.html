PPLdump 利用 KnownDLLs 劫持绕过 PPL 保护并借助 services.exe 转储 LSASS

样本信息

项目 结果
原始文件 ppl_bypass_ppldump_knowdll_hijack_sysmon_security.evtx
文件大小 69,632 字节（68 KiB）
SHA-256 9ac47a1ab7ac5e899dede49a4ea3512f0d3628edb9605981fe78bc0aec6f296f
格式 Windows EVTX，ElfFile / ElfChnk
有效事件数 20 条；物理 Record 1—20
事件来源 Microsoft-Windows-Sysmon + Microsoft-Windows-Security-Auditing
日志通道 Microsoft-Windows-Sysmon/Operational、Security
主机 MSEDGEWIN10
主要运行身份 MSEDGEWIN10\IEUser、NT AUTHORITY\SYSTEM
主要日期 2021-04-22（UTC），北京时间 2021-04-23

PPL 的中文名称是轻量级受保护进程，是 Windows 用来保护重要系统进程的一种安全机制

它的主要作用是：限制保护级别不足的其他进程读取、修改、注入或终止受保护进程

KnownDLLs 劫持是指攻击者设法操纵系统对已知 DLL 的映射关系或加载过程，让目标进程加载攻击者控制的 DLL 代码

PPLdump 是一款用于研究和利用 Windows PPL 保护绕过缺陷的工具，能够在特定存在漏洞的系统版本上，借助用户态技术获取受保护进程的内存转储

它的主要特点是使用用户态技术，而不是必须加载恶意内核驱动来直接关闭 PPL 保护

官方项目也明确说明：其历史版本采用 KnownDLLs 劫持机制，结合 NTFS 事务相关技术实现内存转储

攻击链

PPLdump 由 cmd.exe 启动

  1. 工具直接以 PPLdump.exe 的名称运行，位于当前用户桌面，不是 Windows 系统自带的 services.exe

  2. -v lsass lsass.dmp 明确表示操作目标为 LSASS、输出文件名为 lsass.dmp。命令行只能证实操作意图，本身不能证明转储成功

  3. IntegrityLevel=High，说明 PPLdump 处于高完整性级别。是否具有具体的 PPL 绕过所需系统状态，还应结合后续行为判断

  4. 父进程是 cmd.exe（PID 4864）；日志没有更前一级父进程链，不能据此确认攻击者的初始入口

PPLdump 对 LSASS、winlogon 进行进程访问

ProcessGuid 对应： PPLdump.exe 的 {747f3d96-f415-6081-0000-001040fe4900} 在记录 2、3、4 中保持一致；记录 2、3 目标 LSASS GUID 同为 {747f3d96-6e19-6082-0000-001070650000}，不是仅凭相同的 PID 猜测

权限含义：0x1000=PROCESS_QUERY_LIMITED_INFORMATION；0x1400=PROCESS_QUERY_LIMITED_INFORMATION | PROCESS_QUERY_INFORMATION

NTFS 文件系统事务活动

PPLdump 官方公开原理包含利用 NTFS 事务让替换 DLL 内容能够通过节对象参与受保护进程加载。此处的事务日志和该工作机制吻合

PPLdump 启动异常 services.exe

  1. 这个 services.exe 的 PID 为 7188，由 PPLdump.exe（PID 6316）派生；它不是通常作为系统服务控制管理器运行的 services.exe 实例（稍后日志中另有 PID 624）

  2. 子进程命令行的第一个数字 652，恰好是目标 LSASS 的 PID；后接 lsass.dmp 和一个 GUID，明显不是普通服务控制管理器的惯常命令行

  3. 该进程以 NT AUTHORITY\SYSTEM 身份运行，且 IntegrityLevel=System。这能证明运行身份，但并不能单独从 Sysmon 1 看出 Protected Process Light 的实际保护级别

  4. 子进程 ParentProcessGuid 和第一条 PPLdump 的 ProcessGuid 严格相等，父子进程关系有强直接证据

dbgcore.dll 加载 + LSASS 访问 + lsass.dmp 文件创建

dbgcore.dll 是 Windows 的调试/转储相关模块，它由子 services.exe 加载。这里的模块路径在正常 Windows 系统目录，且日志中签名有效；可疑的是加载主体、时间和后续 LSASS 访问的组合，而不是 DLL 文件本身是恶意文件

0x1410 含 0x10=PROCESS_VM_READ、0x400=PROCESS_QUERY_INFORMATION、0x1000=PROCESS_QUERY_LIMITED_INFORMATION；0x1FFFFF 为包含多类访问位的广泛进程访问掩码。两次访问的 Source/Target ProcessGuid 都一致，能够归入同一组进程

以下是 Record 11 调用栈中有代表性的连续片段

这组调用栈给出了比单纯 GrantedAccess 更强的内存转储相关线索，特别是 dbgcore.dll 与 EventAggregation.dll 同时出现，符合 PPLdump 利用正常组件完成受保护进程转储的设计

转储文件实际创建

不仅 PPLdump 命令行指定了 lsass.dmp，Sysmon 还实际记录了由 PID 7188 的 services.exe 创建桌面上的同名文件，且其 ProcessGuid 与 Record 6 的子进程一致

测验

问题 答案
样本共有多少条有效事件？ 20 条，来自同一个有效 EVTX Chunk。
主要攻击工具名称？ PPLdump.exe。
攻击工具完整路径？ C:\Users\IEUser\Desktop\PPLdump.exe。
工具的原始执行命令？ PPLdump.exe -v lsass lsass.dmp。
PPLdump 的 PID？ 6316。
PPLdump 的 ProcessGuid？ {747f3d96-f415-6081-0000-001040fe4900}。
启动 PPLdump 的父进程是什么？ cmd.exe（PID 4864）。
执行 PPLdump 的用户？ MSEDGEWIN10\IEUser。
PPLdump 的完整性级别？ High。
LSASS 进程 PID？ 652。
LSASS 的 ProcessGuid？ {747f3d96-6e19-6082-0000-001070650000}。
PPLdump 初次访问 LSASS 的权限是什么？ GrantedAccess=0x1000，查询受限的进程信息。
PPLdump 访问了哪些其他安全敏感进程？ 除 LSASS 外还访问了 winlogon.exe（PID 592），权限 0x1400。
新启动的 services.exe PID？ 7188（不同于后来正常的 services.exe PID 624）。
新 services.exe 的运行账户？ NT AUTHORITY\SYSTEM。
新 services.exe 的父进程 PID？ 6316，即 PPLdump.exe。
新 services.exe 命令中出现哪个目标 PID？ 652，正是 LSASS 的 PID。
新 services.exe 命令中出现的 GUID？ a708b1d9-e27b-48bc-8ea7-c56d3a23f99，用途不能单凭该文件完全确定。
哪个进程实际创建了转储文件？ services.exe（PID 7188）。
转储文件创建事件 ID？ Sysmon Event ID 11。
输出文件路径？ C:\Users\IEUser\Desktop\lsass.dmp。
services.exe 加载的关键 DLL？ C:\Windows\System32\dbgcore.dll。
该 DLL 的签名状态？ Signed=true，SignatureStatus=Valid，日志标记签名为 Microsoft Windows。
子 services.exe 对 LSASS 的两次访问权限？ 0x1410 和 0x1FFFFF。
哪个访问权限包含 PROCESS_VM_READ？ 0x1410，其中低位 0x10 即 PROCESS_VM_READ。
哪个访问事件的调用栈明确包含 dbgcore.dll？ Record 11，服务进程访问 LSASS。
两条 Security 事件 ID 是多少？ 均为 4985（文件系统事务状态变更）。
这两条 Security 事件对应哪个进程？ PPLdump.exe（PID 6316）。
两条事务记录的 NewState 是什么？ 48 与 56；本日志只给数值，没有权威状态名。
两条 Security 事件的 TransactionId 是否一致？ 一致，均为 {166192ff-a400-11eb-b76a-0800276b894e}。
KnownDLLs 符号链接是否被本日志直接记录？ 没有。结合 PPLdump 官方工作原理推断其可能参与，但 EVTX 未直接展示。
能否证明 lsass.dmp 已生成？ 能确认文件创建/覆盖事件；无法单凭 EVTX 证明文件内容完整。
能否证明账号密码或哈希已被导出？ 不能，未提供转储内容及凭据解析结果。
能否证明外传？ 不能，此文件没有对应网络连接或数据外传记录。
此份文件与之前普通 LSASS ProcessAccess 题最大的区别？ 本份出现 PPLdump 的命令、由其派生的系统服务进程、dbgcore.dll 调用栈和 lsass.dmp 文件创建事件，证据更完整。
主要 ATT&CK 对应？ T1003.001（LSASS Memory）；KnownDLL 劫持可作为有条件的 T1574.001 参考。
